# Postgres (Supabase) backend

Pulse runs on SQLite by default (`data/pulse.db`, or `PULSE_DB_PATH`), and the
test suite always does. Setting `PULSE_DATABASE_URL` switches the app to
Postgres: the `pulse` schema in the Supabase project **wellpeps-pulse**
(ref `sgzundcnvsmvqdwshcxp`, us-east-1, Postgres 17).

The app never creates or migrates the Postgres schema. You apply the numbered
SQL files here; at startup `StateManager.init_db()` only checks that
`pulse.schema_version` has reached `len(MIGRATIONS)` from `harvey/state.py`,
and stops with a pointer to this file if it hasn't.

## Files

| File | What it is |
| --- | --- |
| `0001_pulse_schema.sql` | Schema `pulse`, equivalent to SQLite migrations v1-v5. Records `schema_version` 5. Idempotent: re-running it changes nothing. |
| `0002_password_management.sql` | SQLite migration v6: `users.must_change_password` (boolean, default false) and `users.password_changed_at`. Records `schema_version` 6. Idempotent (`add column if not exists`). |

## How the schema maps to SQLite

| SQLite | Postgres | Why |
| --- | --- | --- |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `bigint generated by default as identity` | Same ids; "by default" still lets you copy rows over with their ids. |
| `TEXT` ids (`runs`, `actions`, `usage_*`, `sessions`) | `text` | The app generates them. |
| `INTEGER` 0/1 flags (`relevant`, `active`, `breached`, ...) | `boolean` | The app passes Python bools and writes `TRUE`/`FALSE` in SQL, which SQLite stores as 1/0. |
| `TIMESTAMP` | `timestamp without time zone` holding **naive UTC** | Identical semantics to the SQLite build, which stores naive UTC ISO strings. Defaults are `now() AT TIME ZONE 'utc'`, so the session time zone never matters. |
| `REAL` | `double precision` | SQLite REAL is 8 bytes. |
| `*_json` columns | `text` holding JSON | The app encodes and decodes these itself; `jsonb` would reorder keys and change spacing for no gain. |
| `PRAGMA user_version` | `pulse.schema_version` table | One row per applied migration file. |
| audit_log `BEFORE UPDATE`/`DELETE` triggers | plpgsql `pulse.audit_log_append_only()` on `BEFORE UPDATE OR DELETE ... FOR EACH ROW` and `BEFORE TRUNCATE ... FOR EACH STATEMENT` | Postgres also blocks TRUNCATE. The function runs with `search_path = ''`. |

Every table name, column name and index name matches the SQLite schema.
`tests/test_postgres_schema.py` enforces that, so the two can't drift. The
only extras on the Postgres side are `schema_version`, one index on
`mentions(source_id)` (Postgres doesn't index foreign keys by itself), and the
security objects below.

The app sees the same values on both backends: timestamps come back as the
ISO strings Python's `isoformat()` writes (a text codec in
`harvey/db/postgres.py`), and SQL is translated by `harvey/db/dialect.py`
(`?` to `$n`, `INSERT OR IGNORE` to `ON CONFLICT DO NOTHING`,
`CURRENT_TIMESTAMP`, `instr`). Every query also runs through the same
portability check on SQLite, so the SQLite tests catch SQLite-only SQL.

## Security

- Row level security is **on** for every table, with no policy for `anon` or
  `authenticated`, and `anon`, `authenticated` and `PUBLIC` have every
  privilege on the schema revoked. Don't add `pulse` to the exposed schemas
  under Project Settings → API (Data API). It isn't exposed by default.
- `pulse_app` is a `NOLOGIN` role holding the app's privileges, with one
  allow-all policy per table (RLS applies to it, because it doesn't own the
  tables). It can only `SELECT`/`INSERT` on `audit_log`, and can't write to
  `schema_version`.
- The table owner (`postgres`) bypasses RLS, so connecting as `postgres`
  works with no further setup. **Be clear about what that means:** as
  `postgres`, RLS and the `pulse_app` policies do nothing for the app's own
  connection. The protection is then only the revoked grants (anon and
  authenticated can't reach the schema) plus the audit triggers. RLS, and the
  `audit_log` insert-only grant, only take effect when the app connects as a
  login role that is *only* a member of `pulse_app` (not the owner, not
  `postgres`, no BYPASSRLS). See below.
- No password or secret is in any SQL file.

### Least-privilege login (recommended once it's live)

Run this by hand in the SQL editor. Choose the password there; it never goes
in the repo:

```sql
create role pulse_login login password '<choose-a-strong-password>' in role pulse_app;
```

Then connect as `pulse_login` (through the pooler the user name becomes
`pulse_login.sgzundcnvsmvqdwshcxp`).

## Applying it

Pick one:

Apply every numbered file in order (already-applied ones are safe to re-run):

- **Supabase SQL editor:** paste each file and run it.
- **psql:** `psql "$PULSE_DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f db/postgres/0001_pulse_schema.sql`,
  then the same with `0002_password_management.sql`.
- **Supabase MCP / management API:** `apply_migration` with each file's
  contents, named after the file (`0001_pulse_schema`, `0002_password_management`).

To check it worked, run `select * from pulse.schema_version;`. The highest
version should equal `len(MIGRATIONS)` (6).

## Connection string

1. Supabase dashboard → project **wellpeps-pulse** → **Connect**.
2. Pick one:
   - **Session pooler** (recommended; IPv4). Host `aws-*-us-east-1.pooler.supabase.com`,
     port 5432, user `postgres.sgzundcnvsmvqdwshcxp`.
   - **Direct connection**: `db.sgzundcnvsmvqdwshcxp.supabase.co:5432`,
     user `postgres`. IPv6 only unless the IPv4 add-on is enabled.
   - The transaction pooler (port 6543) also works: the app disables named
     prepared statements (`statement_cache_size=0`) and sets `search_path`
     per transaction.
3. Copy the `postgresql://...` URI and put in the database password (reset
   it under Project Settings → Database if you don't have it). Append
   `?sslmode=require`.
4. Put it in `.env` at the repo root, which is gitignored. **Never commit it.**

   ```
   PULSE_DATABASE_URL=postgresql://postgres.sgzundcnvsmvqdwshcxp:<password>@<pooler-host>:5432/postgres?sslmode=require
   ```

The app reads `PULSE_DATABASE_URL` from the environment first, then from
`.env`. When it's set, `pulse run`, `pulse dashboard` and every other CLI
command use Postgres. When it's blank, they use SQLite. A value that isn't a
`postgres://` or `postgresql://` URL is an error, not a silent fallback to
SQLite. Logs only ever show the URL with the password removed.

The pool holds 1-5 connections per process (`harvey/db/postgres.py`).

## Changing the schema

Hard rule (also in CLAUDE.md): a schema change goes in **both** places.

1. Append a SQLite migration to `MIGRATIONS` in `harvey/state.py`. Never edit
   a released one.
2. Add the next numbered file here (`0002_<what>.sql`). Make it idempotent,
   and end it with
   `insert into pulse.schema_version (version, description) values (<len(MIGRATIONS)>, '...') on conflict (version) do nothing;`.
   Enable RLS and add the `pulse_app_all` policy and grants for any new table.
3. Run `.venv/Scripts/python -m pytest -q`. The drift test fails until the
   columns, tables and indexes match.
4. Apply the new file to Supabase **before** deploying the code. Old code
   keeps running on a newer schema; new code refuses to start on an older one.

## Tests against Postgres

`tests/test_postgres_integration.py` (marker `postgres`) is skipped unless
`PULSE_TEST_DATABASE_URL` is set. It **drops and recreates the `pulse`
schema** for every test, so point it only at a disposable database, never at
the Supabase project. It refuses to run if the URL equals the one in `.env`.
The migration creates the cluster-wide role `pulse_app` if it's missing.

```
PULSE_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:5432/pulse_test .venv/Scripts/python -m pytest -q -m postgres
```
